## Context

See `proposal.md` for motivation and scope. Current red-card consequences are
server-authoritative and already cover technical-defeat score generation,
editable-result guards, future Olympic fight reapplication, and active-red
advancement exclusion. Fight-card menus are presentational and receive typed
actions from tournament-page orchestration.

Relevant project skills: `competition-flow`, `disciplinary-cards`,
`backend-architecture`, `frontend-architecture`, and `minimal-validation`.

## Goals / Non-Goals

**Goals:**

- Model fighter withdrawal as nomination-scoped competition state, not as a
  disciplinary sanction.
- Reuse the existing technical-defeat score shape and editable-result rules
  without coupling withdrawal records to disciplinary card lifecycle.
- Keep no-show fighters in generated groups/brackets while excluding active
  withdrawals from advancement.
- Make cancelation precise: reset only technical losses generated by the active
  withdrawal and only while those results remain editable.

**Non-Goals:**

- No changes to yellow/red card issuance, expiration, automatic reds, or card
  delete/edit permissions.
- No broad tournament-page rewrite.
- No new external dependencies.

## Decisions

### Persist withdrawals separately from disciplinary cards

Create a dedicated withdrawal record keyed to tournament nomination and
competitor, with fields for source kind, optional source fight/block/fight
number, reason, excused flag, active/canceled state, and audit timestamps.
Pre-block "No-show" creates an active unexcused record with a system no-show
reason. Fight-card withdrawal creates an active record from the selected fight
and the user-entered reason.

Rationale: withdrawal is not a card, must not expire, must not consume yellows,
must not block other nominations like active red cards, and must have different
cancelation semantics.

Alternative considered: create a manual red card with a special reason. Rejected
because it would incorrectly enter the disciplinary-card lifecycle and
cross-nomination active-red rules.

### Track technical-defeat source explicitly on fights

Do not overload `forfeit_card_id`. Add withdrawal-specific fight linkage (for
example `forfeit_withdrawal_id`) and introduce a typed read-model concept such
as "technical forfeit" that is true for either red-card or withdrawal generated
results. Existing API compatibility can keep `forfeitCardId` while adding a
withdrawal field or source descriptor for new UI/report/rating behavior.

Rationale: reset, reports, ratings, and UI editability need to know whether a
technical result came from a card or a withdrawal. Reusing `forfeit_card_id =
null` would make generated withdrawal losses indistinguishable from ordinary
finished fights or warning technical defeats.

Alternative considered: add a generic `forfeit_source_type` enum and source id.
That is cleaner long-term but larger because existing red-card code and indexes
already use `forfeit_card_id`. A withdrawal-specific nullable link is the
smallest safe model change.

### Extract shared technical-forfeit scoring

Rename or wrap red-card-specific score helpers behind neutral technical-forfeit
helpers, then let both red cards and withdrawals call them. Preserve current
round-win behavior: round-win forfeits use one generated round row per normal
round; aggregate-score forfeits keep the existing 10:0 summary shape.

Rationale: the user-visible score must match red-card technical defeats without
copying scoring constants into a second service.

### Apply withdrawal consequences through competition-side services

Add a competition-owned withdrawal workflow near the existing red-card
consequence flow. It should:

- validate tournament edit access at the route/controller boundary;
- create/cancel withdrawal records transactionally;
- apply editable technical losses to current fights;
- reapply active withdrawals after future fights are generated;
- expose active withdrawal summaries in competition state;
- reset only fights linked to the canceled withdrawal.

Rationale: the `competition-flow` and `disciplinary-cards` skills both place
technical forfeits and advancement effects on the competition side. Withdrawal
is another competition consequence source.

### Define withdrawal applicability by source

Pre-block no-show applies to every generated fight in that nomination involving
the competitor while the withdrawal is active. Fight-card withdrawal applies to
the selected fight and later applicable fights involving the competitor.

For group blocks, "later" means the same block and `fight_number >= source
fight_number`. For Olympic blocks, use the existing round/result-fixed checks:
the selected editable fight is forfeited immediately, and any later generated
fight involving the same competitor is forfeited when generated or when
withdrawal consequences are reapplied.

If both competitors have applicable active technical-forfeit sources in the same
fight, use the existing double-red conflict pattern generalized to technical
forfeits: resolve when policy metrics choose a loser; otherwise surface a
manual pending conflict rather than picking by id.

### Exclude active withdrawals from advancement and technical-match ratings

Group standings should still display withdrawn fighters, but advancement
selection and advancement tie detection must exclude active withdrawals just as
they already exclude active-red competitors. Rating/statistic code that skips
red-card technical forfeits should skip withdrawal technical forfeits through
the new generic technical-forfeit read-model flag.

Rationale: otherwise an absent fighter could advance, or opponents could gain
rating from a non-fought technical result.

### Keep frontend widgets store-free

Extend tournament orchestration/composables and the competition store/API layer
with typed withdrawal actions. Tournament fight widgets receive action props and
emit refresh events, following the existing card-issuance pattern. The
registered-fighter list receives a no-show action prop and renders it only from
server-derived nomination/block state plus access flags.

Rationale: this matches `frontend-architecture` and the existing
`FightCard`/`IssueCardDialog` flow.

### Present withdrawal markers like card markers

Expose active withdrawal summaries keyed by nomination competitor/fighter so the
frontend can render them wherever the fighter name appears in the affected
nomination. Use Lucide `TriangleAlert` from the existing `lucide-vue-next`
package and mirror the disciplinary-card marker placement pattern in
registration lists, group displays, and fight participant labels.

Use base icon color for excused withdrawals and red for unexcused withdrawals.
The marker title should be built from the stored reason as
`боец снят: [reason]`; no-show records store `неявка` as their reason, so they
naturally display `боец снят: неявка`.

Rationale: this keeps the visual language consistent with active-card hints
without mixing withdrawal data into disciplinary-card state.

## Risks / Trade-offs

- [Risk] Withdrawal and red-card forfeits may diverge over time. -> Mitigation:
  shared technical-forfeit scoring helpers and focused tests for both sources.
- [Risk] Canceling a withdrawal could clear unrelated scores. -> Mitigation:
  link generated fights to the withdrawal record and reset by that link only.
- [Risk] Future Olympic fights can be created after the withdrawal source fight.
  -> Mitigation: reapply active withdrawals in the same places that currently
  reapply red-card forfeits after fight generation/progression.
- [Risk] Existing frontend code treats only `forfeitCardId` as non-editable.
  -> Mitigation: introduce a generic fight technical-forfeit flag in the mapper
  and update score editing, result display, and round-time visibility to use it.
- [Risk] Withdrawal markers could appear in other nominations for the same
  fighter. -> Mitigation: key marker state by nomination competitor or
  tournament-nomination context, not only by fighter id.
- [Risk] Two active technical-forfeit sources can target the same fight. ->
  Mitigation: generalize the existing double-red pending-conflict policy instead
  of inventing a new arbitrary ordering.

## Migration Plan

1. Add database schema for withdrawal records and withdrawal-linked fight
   forfeits.
2. Backfill is not required because existing tournaments have no withdrawal
   records.
3. Deploy backend and frontend together because competition-state response shape
   and fight editability flags change.
4. Rollback requires dropping withdrawal-created data or leaving it unused by
   the previous application version; do not roll back after withdrawal records
   have been used in production without a data cleanup plan.
